# Bound broker requests without losing ambiguous order outcomes

## Problem

The paper runtime can block indefinitely in a broker SDK request. Adding a timeout alone is unsafe: an order POST can reach Alpaca and then lose its response, while the current executor records every exception as `ERROR`. The evaluator and counterfactual path treat `ERROR` as an order that never left, fill reconciliation scans only `SUBMITTED`, and the loop's duplicate guard expires after 30 minutes. Retrying after an ambiguous POST can therefore double exposure.

## Measured baseline (2026-10-11)

- The Alpaca SDK is pinned to 3.2.0. Its `REST._request()` builds request options without a timeout and invokes `_session.request(method, url, **opts)`; the session therefore inherits Requests' no-timeout default.
- The SDK defaults to three retries, three seconds between retryable responses, and retries HTTP 429/504. The prior real, retry-disabled paper read sample was 40 attempts, 0 failures, aggregate p50 25.036 ms, p95 27.248 ms, max 90.247 ms. This small read-only sample does not measure order POSTs or outages.
- A source scan found 29 broker method call sites across `src/autopoiesis/` and `tools/`; seven `REST()` constructors are spread across CLI, doctor, and operator tools rather than one configured factory.
- `AlpacaPaperExecutor.execute()` returns `ERROR` on any submit exception while preserving a deterministic client order ID. `FillReconciler.pending()` only scans `SUBMITTED`. `TradingLoop._identical_order_already_in_flight()` checks only similar `SUBMITTED` orders and forgets them after 30 minutes. Startup reconciliation compares open broker IDs and cannot recover a missing submit response by client order ID.
- SIGTERM only sets a flag. Synchronous daemon maintenance/LLM calls are not cancellable; the existing 30-second systemd stop timeout is not being changed by this work.

## Success criteria

1. Every app-created Alpaca client has the same explicit connection/read timeout policy, zero SDK retries, and a test proving the request layer receives the configured timeout object. The policy is fixed in code and cannot be weakened by model output or an environment override.
2. The implementation states the exact guarantee: connection timeout, read-inactivity timeout, and urllib3's total budget are supplied to each request. Because Requests/urllib3 cannot guarantee a hard wall-clock deadline under slow-trickle responses or every resolver stall, documentation must not call this an absolute process deadline or use it alone to justify `TimeoutStopSec`.
3. Before every submit POST, the journal durably records and `fsync`s an `ORDER_SUBMISSION_INTENT` containing the client order ID and exact order identity (cycle, symbol, side/action, quantity, type, TIF, strategy). If that append or fsync fails, no POST is sent. An intent without a durable acknowledgement or resolution is unresolved after restart, including a crash before the POST was sent. This conservative false positive is preferable to a duplicate order.
4. A submit exception or a crash after intent becomes a distinct `SUBMISSION_UNKNOWN` state. The existing `ERROR` state is not used as evidence that the broker did not accept the order. If the broker returns success but appending the cycle/acknowledgement fails, the already durable intent still blocks future orders and is recovered by client ID after restart. An acknowledged order without a cycle row remains in the daily order-attempt cap and operator/evaluation counts; a failed reporting append cannot erase an order from limits.
5. Any unresolved intent/unknown blocks all later non-HOLD submissions, including other symbols and cycles, without changing Guardian rules. The block does not expire with the 30-minute duplicate window. On upgrade, every legacy `CycleRecord.execution.status == ERROR` with a client order ID and no definitive broker rejection evidence is migrated into the unresolved projection and looked up by that exact ID before trading is enabled. Missing lookup leaves the system blocked; legacy ERROR is never assumed to mean no POST. Malformed journal lines, invalid schema, failed reads, and missing required generations also fail closed for this safety projection; `read_events()` currently records dropped lines but does not raise, so the gate must explicitly reject `last_dropped_lines > 0` (and inspect both event and cycle scans).
6. Reconciliation queries every unresolved client order ID. A returned exact order is durably resolved and projected as known by broker ID for startup open-order comparison. A found order with nonterminal status becomes a normal pending fill item. Fill polling is cumulative: persist each distinct broker cumulative snapshot and derive incremental fills from monotonic quantity changes, deduplicating by client order ID plus observed cumulative quantity/status/average price (or explicitly accepting an average-price-only correction); do not stop polling after the first partial fill. If the broker changes cumulative average price without increasing quantity, preserve that correction as a newer snapshot and make PnL/holding projections use the latest snapshot per order rather than summing cumulative rows. `pending_cancel` is not terminal; only confirmed filled/canceled/expired/rejected statuses close polling. A `replaced` order is followed through its broker replacement ID and linked order for startup matching/fill reconciliation; if the relationship is missing, inconsistent, or cannot be fetched, keep the safety block and require operator investigation. Absence, timeout, or error leaves an unknown unresolved and keeps the global block active. No automatic resubmit occurs.
7. Event projection defines lifecycle semantics: unresolved intent/unknown is outstanding and inconclusive (not a fill, rejection, error-rate penalty, or proof of non-submission); resolved open/partially-filled remains outstanding and is reconciled; broker-confirmed fill contributes only its confirmed quantity/price. A canceled/expired/rejected terminal state is no-fill only when broker-confirmed cumulative fill is zero; otherwise preserve the confirmed partial fill and reconcile remaining quantity to terminal state. These outcomes are counted separately from Guardian rejection. Counterfactual rows for unresolved attempts are explicitly inconclusive and excluded from informative strategy scoring. Evaluator counts attempts/unresolved separately, does not increase `execution_errors` for ambiguity, and never includes it in PnL.
8. There is no operator action that clears an unknown based only on a “not found” response. Add `docs/runbooks/ambiguous-order-recovery.md`: stop the paper process, preserve journal and broker evidence, check order history and positions by client ID/time window, and keep the global block until positive broker evidence or documented broker-support resolution is available. Any manual resolution record must include operator identity, timestamp, evidence reference, and terminal disposition; it cannot authorize resubmission by itself. No tool/command silently clears this state. A documentation check verifies the runbook describes these steps and the exact event fields.
9. No live endpoint, order submission, service restart, or risk-limit change is used in validation. Tests simulate broker acceptance followed by a lost response using explicitly labelled fake test behavior only; it is not evidence about real broker execution.

## Proposed minimal design

- Introduce one `broker_client` factory/configuration path used by CLI, doctor, replay/smoke tools, and the sampler. Use an audited Requests `Session` subclass that creates a **fresh** `urllib3.Timeout(total=7, connect=2, read=5)` for each `request()` and forwards it into `Session.request`; a test must exercise the SDK 3.2.0 `REST._request()` path and assert the adapter's `send()` receives that exact timeout. Do not set an unused `Session.timeout` attribute or reuse a stateful Timeout object. Set SDK retries to zero. These values exceed the observed read max by a wide margin but are engineering defaults, not statistically derived outage guarantees; keep them fixed until a component-level benchmark justifies a change.
- Keep all network client construction in that helper. Fail startup if the supported SDK/session contract is unavailable. Ensure the sampler uses the same request policy for future runs, but do not re-run the real broker sample in this work unit.
- Extend `JournalEvent` with intent/acknowledged/unknown/resolved/fill-snapshot event types. The write-ahead intent is the safety boundary before network I/O. Emit an acknowledgement event only after a successful submit response has been received and its order ID/client ID validated, and append it before the cycle projection. If cycle append fails, the acknowledgement event itself carries broker order ID/status and is included in startup known-order, pending-fill, daily-cap, and attempt-count projections, so the accepted order remains visible and recoverable without a `CycleRecord`. Event-backed counting deduplicates by client order ID and coexists with legacy cycle-only records without double counting; unresolved durable intents count conservatively toward the daily attempt cap. The intent continues to block until acknowledgement is durably projected. The `CycleRecord` stays the reporting projection, not the write-ahead record. State is derived from ordered journal events by client order ID; no in-place mutation or status overwrite.
- Make the loop's fail-safe gate inspect the full event and cycle history before any new non-HOLD order. Each scan checks dropped-line counters; a corrupt/torn record means refusal. If intent append/fsync fails, executor must not call the broker. If response arrives but subsequent journal append fails, propagate the failure and rely on the durable intent for startup recovery.
- Extend startup and fill reconciliation to recover unresolved intent IDs by exact `get_order_by_client_order_id`. A returned order is durably resolved and its broker ID participates in the known-order set, preventing a false “extra broker order” mismatch. Resolved open/partial orders feed fill reconciliation. Persist cumulative fill snapshots, then project per-order latest cumulative quantity/average price for holdings and PnL; derive new incremental quantity only for audit display, not by summing snapshots. Re-poll after partial fills and after `pending_cancel`; only confirmed terminal statuses stop polling. Follow a `replaced` order through its broker-provided replacement ID and reconcile the replacement; missing/inconsistent links fail closed for operator investigation. Terminal rejected/canceled/expired orders with cumulative fill zero produce a resolved no-fill outcome; with a positive cumulative fill, preserve that quantity/price as a confirmed partial fill and mark only the remaining quantity terminal. Resolution and fill projection must be idempotent across restart.
- Ship the named runbook `docs/runbooks/ambiguous-order-recovery.md` alongside the code and verify its operator steps, evidence fields, and no-resubmit/no-clear-on-not-found policy.
- Add a journal archive manifest with a monotonically increasing expected archive generation (and checksums/size for each completed archived file) before claiming completeness for newly written history. Validate archive sequence and manifest at the fail-closed safety gate; a gap, mismatch, or unexpected missing generation blocks submissions. Bootstrap is a one-time audited migration: require contiguous observed archives and operator attestation that the current journal is the trusted baseline before enabling trading; a manifest generated from whatever files happen to exist must not silently bless an already-missing generation. For fresh installs with no history, the empty baseline is explicit. Document that this proves history only from the attested baseline forward. Test gap, deletion, checksum mismatch, rotation crash ordering, bootstrap refusal/attestation, and fresh-clone initialization.
- If broker lookup is not found or fails, retain the block indefinitely. The operator runbook must explain safe evidence gathering and explicitly forbid clearing/resubmitting based only on absence. No auto-clear or “definitely absent” inference is added.
